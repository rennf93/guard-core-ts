## [Unreleased]

### Added

- Config: `exemptIps` on `SecurityConfig` (array of IP/CIDR strings, empty by default), the port of the reference's `exempt_ips` (guard-core #117/#118). It is noise reduction for known-friendly automation, not immunity: a non-empty `whitelist` denies every unlisted IP, so there was no way to let a few trusted clients (monitoring probes, VPN egress, a partner's server) skip throttling on a public API. An exempt match sets `request.state.isExempt` under the same conditions as `isWhitelisted`, computed in `IpSecurityCheck` from the deny-check outcome (`is_allowed`), so exemption never adds or relaxes a deny path; the exempt match reuses the whitelist matcher (`isIpInWhitelist`), so exact, CIDR and IPv4/IPv6-family semantics stay identical. The skip set matches the reference: `RateLimitCheck`, `UserAgentCheck` and `CloudProviderCheck` now honor `isWhitelisted || isExempt`, while `SuspiciousActivityCheck` honors `isWhitelisted` only, so penetration detection, its violation counting and its escalation still run for exempt IPs (an attack payload from an exempt IP is still blocked; a scanner needs per-route `bypass(["penetration"])`, widening the field later is backward compatible). Still applies to exempt IPs, deliberately: the blacklist, the whitelist deny path, dynamic bans and per-route `requireIp`/`blockIp` rules (a route-level `ipWhitelist` takes over the global lists and clears both flags, exactly like the reference `skip_ip_lists` gate). Entries are validated at construction like `whitelist`/`blacklist` (invalid entry fails closed). The IP check now also enforces dynamic bans (the reference `_check_banned_ip` stage the port had skipped): `initializeSecurityMiddleware` wires the registry's `IPBanManager` into `IpSecurityCheck` (optional constructor arg, standalone pipelines and direct constructions keep working), banned IPs get 403 `IP address banned` before the flag resolution, honoring route `bypass(["ip_ban"])` and passive mode. `GuardRequestState` documents the two flags
- Detection: the reference's excluded-field config surface is now available: `excludedDetectionParams` and `excludedDetectionBodyFields` on `SecurityConfig` (empty by default). `excludedDetectionParams` skips a query parameter's whole pair from penetration detection (`key.lower() in excluded_params` in `_scan_query_params`), and `excludedDetectionBodyFields` skips urlencoded form pairs and multipart parts by field name and whole JSON subtrees by key at any nesting depth: `scanRequestWithManager` now takes the resolved config (the middleware path passes it through `detectPenetrationPatterns`, the standalone path uses the default manager's config), threads the body-field exclusion into the embedded-JSON walks of query and header values, and skips excluded multipart parts via a new `exclusionKey` on each `MultipartEntry` (the disposition name, null for unnamed parts, so the `file` fallback label never suppresses a part without a name, exactly like the reference). Entries are matched verbatim while scanned names and keys are lowercased first, mirroring Python's `_STR_SET_ADAPTER` + `key.lower()` membership semantics. One routing divergence against the reference is corrected on the way: a JSON-content-type body whose walk parses cleanly is now final (the raw blob only scans on parse failure, mirroring `_scan_request_body`'s `json_hit is not None` check, the same fall-through shape as the Go and PHP ports), so an excluded JSON key's subtree stays excluded instead of leaking through the blob rescan. Verified against the reference engine: a JSON body with an excluded nested key does not detect, while the raw query value still scans after an embedded walk whose every leaf was excluded (defense in depth)
- Detection: multipart/form-data bodies are now parsed and scanned part by part instead of falling through to the whole-body blob scan, completing the family's body-surface parity (guard-core commit 5f399234, mirrored by the merged Go and PHP ports). A hand-rolled line-based scanner mirrors the reference email-parser tolerances: preamble and epilogue discarded, raw header names and case kept in wire order, folded header continuations preserved with their raw break, the first colonless line opening the payload, the line terminator before a boundary belonging to the delimiter, nested multipart containers walked in place, and a missing closing boundary keeping the part parsed so far. Each leaf part scans its field name, then its filename entry (`filename="..."` with RFC 7578 quote unescaping and get_filename's RFC 2231 `filename*` fallback), every part header, and the payload under `request_body:multipart_field`; a body that does not parse into at least one leaf part (no boundary parameter, boundary mismatch) keeps the whole-body blob fallback
- Detection: binary-dense file-part payloads are reduced to printable islands before pattern scanning. A part payload whose binary artifact characters (control bytes, U+FFFD, surrogate-escaped bytes) fill at least a fifth of it is cut into its maximal printable runs, and only runs of at least `detectionBinaryMinRunLength` (new SecurityConfig field, default 16, bounds [4, 1024]) are handed to the scan as individual values, so compressed or encrypted uploads stop producing attack-shaped matches whose rate grows with file size while text embedded in uploads (a script inside a PDF, a path inside an archive) still scans in full. Nothing detects across island boundaries; text parts without a filename and whole-body fallback scans keep their full scan so raw-body signature coverage stays intact
- Detection: urlencoded form bodies now split through a `parse_qsl(keep_blank_values=True)` port (valueless names kept, empty chunks dropped, plus-as-space, tolerant percent-decoding with valid UTF-8 runs decoded as text), replacing the `URLSearchParams` iteration whose semantics drifted from the reference on edge cases

### Fixed

- Detection: separator-prefixed recon probes such as `\default` or `\README.md` scanned in query, body or form-field values now detect again. The configured pipeline's preprocessing folds LDAP hex escapes (`\de` into `Þ`) before the pattern table runs, so the probe arrived mangled on the processed views, and the recon-category rows were excluded from the raw view, leaving no view that saw the original value. All 21 recon rows now join the signal-preserving raw view (a `DETECTION_RECON_RAW_VIEW_PATTERN_SOURCES` set derived from the table, mirroring `guard_core/handlers/_suspatterns_pattern_table.py`, upstream commit 81cf07f1), their processed-view runs stay intact, the #116 leading-separator probe gate applies unchanged to raw-view matches (bare words stay innocent outside url_path/unknown), and raw-pass threats are deduplicated against the processed-view threats keyed on (pattern, match text) so a row matching both views counts once. Parity with guard-core-rs #21, guard-core-go #16 and guard-core-php #16
- Detection: the live middleware now runs the FULL canonical pattern table through `SusPatternsManager.detect` for every request surface (query param names and values, URL path, header names and values, JSON body keys and leaves, form fields, raw blob), exactly mirroring the reference detect flow (`guard_core/_utils/penetration_detection.py` + `detection_scan.py`). Previously the `SuspiciousActivityCheck` only ran a hardcoded 7-pattern shortcut, so the TypeScript middleware detected far less than every other family: recon probes, tautologies, event-handler XSS, NoSQL operator keys and all case/encoding variants that live only in the 157-row table were missed. JSON leaves embedded inside non-body values carry the `:embedded_json` context suffix so the engine's per-context gates (recon bare-word rule, source-extension probe rule) apply to them; body JSON values scan as `request_body` per the reference context matrix. The retired 7-pattern shortcut path is gone; the public `detectPenetrationAttempt` export now delegates to the same engine on a shared default manager
- Adapters: block and error responses are `text/plain; charset=utf-8` carrying the message itself, instead of `application/json` wrapping it in a `{detail: ...}` envelope, mirroring the Python family convention (fastapi-guard #144). Applies across the express, fastify, hono and nestjs response factories (redirect responses keep no body, custom_error_responses messages stay plain text), and a `customResponseModifier` that sets its own content type still wins
- Detection: recon whole-value rows with an optional leading path separator no longer flag bare words such as "default" or "README.md" scanned in query/body contexts; bare words remain probes as the url_path (or in unknown contexts) and separator-prefixed paths are still threats. Parity with guard-core #115/#116 (commit 08f79d67)
- Logging: `sanitizeForLog` now emits pure ASCII like the reference `_sanitize_for_log` (guard-core commit f5d53ca5, log half). Control characters and every non-ASCII code point become `\uXXXX` escapes (lone surrogate-escaped bytes in the 0xDC80-0xDCFF range become `\xNN`), so log lines can never raise on legacy code pages such as Windows cp1252

## [1.0.0] - 2026-03-27

### Initiial release

- Initial release of the @guardcore TypeScript ecosystem
- **@guardcore/core**: Framework-agnostic security engine (TypeScript port of guard-core Python)
  - 6 protocol interfaces (GuardRequest, GuardResponse, GuardResponseFactory, GuardMiddlewareProtocol, GeoIPHandler, AgentHandlerProtocol, RedisHandlerProtocol)
  - 44-field SecurityConfig with Zod validation and cross-field validators
  - 17-check SecurityCheckPipeline (Chain of Responsibility pattern)
  - 75 suspicious pattern definitions with 17 context sets
  - Detection engine: PatternCompiler (re2-wasm + worker_threads fallback), ContentPreprocessor, SemanticAnalyzer, PerformanceMonitor
  - 9 handlers: RedisManager, IPBanManager, RateLimitManager, CloudHandler, SusPatternsManager, SecurityHeadersManager, BehaviorTracker, DynamicRuleManager, IPInfoManager
  - HandlerRegistry pattern (no global singletons, test-friendly)
  - 20-method SecurityDecorator with TypeScript mixin composition
  - Full utils module: IP extraction, penetration detection, logging, agent events
  - Edge runtime support via Uint8Array protocols and re2-wasm
- **@guardcore/express**: Express middleware adapter with raw body preservation
- **@guardcore/fastify**: Fastify plugin adapter with onRequest/onSend hooks
- **@guardcore/nestjs**: NestJS middleware + GuardModule.forRoot() with DI
- **@guardcore/hono**: Hono middleware factory (edge-safe, lazy initialization)
- 681 tests with 100% statement/line coverage across 31 test files
- Comprehensive CLAUDE.md with TypeScript development standards
